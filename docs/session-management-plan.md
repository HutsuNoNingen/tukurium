# セッションを作成・選択し、参加後はKokoSyncで同期する

作成日：2026-10-23 / 状態：当初の実装計画。ローカルのセッション管理は実装済み。公開サーバーへ配置済み。

現行仕様：HNだけで開始し、同じHNなら同じ利用者・ライブラリを使う。接続用パスワードと本人情報ファイルの移行は不要。以下の当初案にある「同名でも別ユーザー」等は置き換え済み。詳しくは [公開サーバーの構成](deployment.md) を参照。

実装追記：ローカルサーバー経由の作成・一覧・参加・終了と、KokoSyncへの接続を追加した。固定ルーム版も残している。現在の操作と制限は [ローカル管理機能](local-services.md) を参照。以下は当初の設計方針である。

**ユーザー名を入力したあとに、セッションを作るか、一覧から参加するかを選べるようにする。** セッションの登録・検索・参加許可は管理APIが扱い、参加後のワールド同期は現在のKokoSync経路を使う。

初版では、作成者のPCで動くRust Engineがワールドのホストになる。作成者が終了すればセッションも終了する。常時稼働する専用ホストやホストの自動交代は、この計画の初版には含めない。

関連する計画：[アセット保存サーバーの実装計画](asset-library-implementation-plan.md)。ユーザーIDと本人用キーは共通で使い、セッションごとに別アカウントを作らない。

## 1. 現在は固定ルームへ直接入っている

現在の配布設定は `session: workshop` で、全員が同じ `kokoverse/workshop` へ参加する。Go Adapterは最初に `host` というpeer名で接続を試し、重複で拒否された場合にゲストとして接続する。

GodotとRust Engine、Rust EngineとGo Adapterは、それぞれPC内のTCPで通信する。PC間の配送はKokoSync中継を通り、配布版の中継への接続はWSSを使う。表示名の入力と、中継へ接続するための認証は別の処理である。

| 現在流している情報 | 担当 |
|---|---|
| 編集要求、操作結果、途中参加の初回状態 | KokoSyncの相手を指定した配送 |
| ホストが確定した変更 | KokoSyncから参加者へ配信 |
| アバターの姿勢、移動中のプレビュー | KokoSyncの最新値の配送 |
| モデル・動画などの素材 | Engineが分割し、KokoSyncで転送 |
| ワールドの保存 | ホストPCのローカルファイル |

KokoSyncはデータを運び、Rust Engineは編集の採否とワールドの正本を管理する。現在の実装は [runtime.md](runtime.md)、接続方針は [kokosync.md](kokosync.md) を参照する。

## 2. 作成者と参加者を、接続する前に決める

固定のルーム名を、管理APIが発行するセッションIDへ変更する。KokoSyncのルーム名は `kokoverse/<session_id>` とし、利用者が付けるセッション名とは分ける。同名のセッションを作っても混ざらない。

作成者をホストとして登録したあと、明示的にホストモードで起動する。参加者はゲストモードで接続する。管理対象のセッションでは、現在の「最初に接続した人がホスト」という自動判定を使わない。

管理APIはホストとセッションの対応を記録し、役割を確認できる短期の参加証明を発行する。初回同期では、接続中のpeer・接続世代と、その証明で確認したホストの対応を検査する。想定したホストを確認できなければ、別の参加者へ自動的に切り替えずエラーにする。

初版は一覧に掲載する公開セッションを対象とする。招待限定・非公開セッションは、実際のKokoSync参加を制限する経路まで整えてから追加する。推測しにくいルーム名や、一覧に表示しないことだけをアクセス制御にはしない。

## 3. 開始画面から作成・参加へ進む

```text
ユーザー名入力・本人情報の準備
  └─ 開始画面
       ├─ セッションを作る
       │    → 名前と初期ワールドを選ぶ
       │    → 管理APIへ登録
       │    → ホスト起動・KokoSync接続
       │    → 準備完了を登録して入室
       └─ セッション一覧
            → 参加先を選ぶ
            → 参加情報を取得
            → ゲストとしてKokoSync接続
            → ホストの初回状態を受け取って入室
```

作成画面の初期ワールドは、まず「新規ワールド」か「自分のローカル保存」の二つにする。ライブラリやクラウドからのワールド起動は後続工程とし、アイテムの保存機能と混同しない。

一覧には、セッション名、作成者、状態、最終更新時刻を表示する。人数は取得できるようになった時点で追加し、管理APIへの報告値と実際の接続人数に一時的なずれがあり得ることを前提にする。停止済みや準備中のセッションへは参加できない。

準備中、接続中、初回状態の取得中、接続失敗を画面で区別する。初回同期が終わるまで編集を許可しない。終了時は開始画面へ戻れるようにし、別のセッションへ移る場合は古い接続・描画・保留操作を破棄してからつなぐ。

## 4. 管理APIとKokoSyncの担当を分ける

| 担当 | 責務 |
|---|---|
| 管理API | ユーザー識別、セッション一覧・作成・終了、ホスト登録、参加情報と短期証明の発行 |
| Rust Engine | ワールド読み込み、編集検証、スクリプト実行、初回状態と差分、保存 |
| Go Adapter / KokoSync | 指定されたルームへの接続、確実な配送、最新の姿勢の配送、切断通知 |
| Godot | 開始画面、一覧、作成・参加操作、進捗、ワールドの表示 |
| アセット保存機能 | 保存版・素材の保管と、権利に応じた取得 |

管理APIは計画中の `crates/asset-server` と同じプロセス・DBに追加する。セッション機能のために別のサービスを増やさず、内部の処理はアセット保管と分ける。

参加後の移動や編集を、管理API経由へ移すことはしない。既存の同期を保ち、クラウドに保存された素材はアセットAPIから取得する。ローカルから取り込んだ素材の既存転送は、アセットAPIへの切り替えが成立するまで残す。

## 5. 保存先とセッションの寿命を分ける

セッションIDは、その開催を識別するIDである。保存したワールドのIDや保存先とは分ける。同じ保存ワールドを翌日に開き直す場合も、新しいセッションとして登録する。

ホストのワールド保存先は、選んだワールドごとに分ける。現在の固定された `.run/world.json` を、すべてのセッションで無条件に使い回さない。新規ワールド作成時は新しい保存先を用意し、既存ワールドを選んだ場合だけその保存先を読む。

同じ保存先を二つのホストから同時に書き換えないように排他する。ゲストはホストの保存先を自分の保存先として扱わない。

## 6. 準備・稼働・切断を管理する

| 状態 | 意味 | 一覧からの参加 |
|---|---|---|
| preparing | 登録済み。ホストの起動やワールド読み込みを実行中 | 不可 |
| ready | ホストがKokoSyncに接続し、初回状態を渡せる | 可 |
| reconnecting | ホストが一時切断から復帰中 | 新規参加不可 |
| ended | 終了、起動失敗、または復帰期限切れ | 不可 |

ホストは管理APIへ定期的に稼働を報告する。初期値は5秒間隔、失効まで30秒を案とし、試験で調整する。正常終了では明示的に終了を登録し、強制終了では報告の期限切れで一覧から外す。起動途中で失敗した場合も、準備中のまま残さない。

管理APIだけが不通になっても、既存のKokoSync接続が直ちに切れたとは扱わない。新しい参加情報は発行せず、接続中の画面には管理サービスとの通信失敗を表示する。すでにendedへ移った場合は、通信の回復だけで再公開せず、ホストが明示的に新しいセッションを作る。

管理APIへの稼働報告だけでreadyにしない。ホスト側のKokoSync接続状態も報告に含め、切断を検出したらreconnectingへ移す。同じホストの一時復帰は認めるが、endedのセッションを古い報告で復活させない。

初期同期時と同様に、再接続では接続世代を確認する。ゲストはホストの確定状態を取り直し、切断前の未確定操作を自動で再送しない。ホスト交代は行わず、復帰しなければ参加者へ終了を表示する。

正常終了時はワールドの保存完了を確認してから退出する。管理APIへ終了を通知できなくても、ローカル保存は完了させ、一覧の終了処理は期限切れで補う。強制終了では最後の保存以降の変更が失われ得る点は現在と同じである。

## 7. 追加するデータとAPI

セッションの記録には、ID、表示名、作成者ID、ホストのユーザーID、KokoSync接続先・ルーム、状態、作成・終了時刻、最終稼働報告、ホストの接続世代を持たせる。管理APIに、ホストPC内の保存ファイルの実パスや本人用キーを載せない。

| API案 | 操作 |
|---|---|
| `POST /v1/sessions` | セッションをpreparingで登録し、作成者へ接続情報とホスト用の初期証明を返す |
| `GET /v1/sessions` | 参加できる公開セッションをページ単位で取得する |
| `GET /v1/sessions/{id}` | 現在の状態と、利用者に開示できる情報を取得する |
| `POST /v1/sessions/{id}/join` | 状態・参加条件を確認し、接続情報と短期証明を返す |
| `POST /v1/sessions/{id}/heartbeat` | 登録されたホストが稼働状態を報告する |
| `POST /v1/sessions/{id}/end` | 作成者または認可されたホストが終了する |

既存計画の `/v1/session-tickets` は、このjoin処理へ統合する。短期証明にはユーザー、セッション、役割、期限、接続との対応を検証する情報を含め、別セッションへ流用できないようにする。検証方式は実装契約で確定し、同じ役割のAPIを二重に作らない。

作成要求の再試行には一意なキーを使い、同じ要求で複数のセッションを作らない。readyへの変更、稼働報告、終了は、名前やpeerの自己申告だけで許可しない。

現在の中継認証情報と、個人の本人用キーは別に扱う。中継の既存認証を、新しいユーザー識別の代わりにはしない。非公開セッションを追加する際には、参加証明と中継側の入室制限を接続する必要がある。

## 8. 実装順と完了条件

| 工程 | 作るもの | 完了条件 |
|---|---|---|
| 1 | 管理APIのセッション記録、一覧、作成、終了、期限切れ | 再試行で重複せず、終了・失効したものに参加できない |
| 2 | Engine・Adapterへ接続情報を渡す処理、役割の明示、保存先選択 | 異なる二つのルームが混ざらず、作成者が各ホストになる |
| 3 | Godotの開始・作成・一覧・参加画面 | ユーザー名入力後、画面から作成と参加ができる |
| 4 | ホストの準備完了・稼働報告、切断・復帰、終了処理 | 準備途中の参加や古いセッションの復活を防ぐ |
| 5 | アセット保存計画の本人・利用権との接続 | 参加する権利とアイテムを保存する権利が混ざらない |

検証では、同じ名前の二つのセッションを同時に作り、別々のワールドで編集できることを確認する。続けて、途中参加、ホスト起動失敗、ホストの強制終了、一時切断からの復帰、別セッションへの移動を試す。

別セッションの差分・姿勢・素材要求を受けても採用しないこと、想定外のpeerから届いた初回状態を拒否することも確認する。作成者が終了したあとに別の参加者が自動でホストにならないことを試験に含める。

この段階で実現するのは、ユーザーが選んで開始できる一時的な共同作業の場である。作成者がいない時間も動くワールドが必要になったら、同じRust Engineを専用ホストで起動する管理機能を追加する。
