# UGCパーツを増やす計画

状態：段階0の土台と段階1のWorldTextを実装済み。以降の部品は未実装。作成日：2026-10-24。
対象：ワールド内で作者がパーツを組み合わせ、操作できる作品を作る。比較調査は[UGCコンテンツと部品](ugc-content-capability-survey.md)を参照する。

## 目標と設計上の約束

最初の到達点は、参加者がワールド内で「文字付きの操作盤」を組み立て、ボタンで別の部品の色を変更し、作品ごと複製・保存できること。次の到達点は、同じ部品群を使って共同テトリスを作れること。作品専用の通信経路や、テトリス専用のゲーム規則を製品コードへ追加しない。

- Rust ECSのSlotと役割別Componentが共有状態の正本。型・値域・対象・競合の検証と保存をComponent登録表へ置く。
- Godotはパーツの描画、ローカルなホバー・押下・フォーカスを担当する。作者のLuaにGodotノードやネットワーク接続を直接渡さない。
- アセット本体は既存のハッシュ検証済み保管層、Componentには参照と設定を置く。手続き的な形はまず生成器の型とパラメータを同期する。
- 共有WriteとローカルDriveを分け、毎フレームの表示結果を共有の確定値へ書き戻さない。
- ライセンス・所有者によるワールド操作制限はこの計画へ含めない。参加者の確認、値の検証、競合チェックは維持する。

## 実装順

進捗：描画部品を持たないSlotの作成、同期、複製、保存復元、共有作成パネルからの作成を実装済み。`CreateSlot` は初期Componentと親からの相対位置を受け取り、新規Slotをまとめて確定する。`AddComponent` / `RemoveComponent` は登録表に基づく検証と競合チェックを備え、インスペクタから `MeshRenderer` と `WorldText` を付け外しできる。以降のComponentも同じ登録経路へ追加する。

`WorldText` は空Slotにも付けられ、文字と色を共同編集できる。`UgcCanvas` 以下のUI要素とレイアウトはまだ未実装。

フィールド参照をコード欄へ渡して `Read` / `Write` / `Drive` を選ぶ操作を実装済み。登録表が許可する別Slotの表示フィールドにも書き込みとローカルDriveが届く。ボタンUIと作品内の操作イベント、汎用Bindingは引き続き段階2・3の対象。

段階ごとに、前段の部品だけでも作れるものを残す。括弧内のComponent名は仮称。

| 段階 | 追加するパーツ・仕組み | 作れるものと完了条件 |
|---|---|---|
| 0. 付け外しの土台 | 登録表で扱う `AddComponent` / `RemoveComponent`、描画部品を持たないSlot、パーツ追加パレット | 空のSlotへ表示部品を付け、外し、複製・保存・途中参加でも同じ構造になる |
| 1. 表示 | ワールドに直接置く `WorldText`、既存WorldPanelに載る `UgcCanvas`、その子の `UiText` / `UiImage`、縦横・格子レイアウト | 作者が看板とスコア表示用パネルを作り、文字・色・寸法を共同編集できる |
| 2. 操作 | `UiButton`、`UiToggle`、`UiSlider`、後から同じイベント型を使う物理ボタン | どのパーツに、誰が、どの操作と値を送ったかをRustで検証し、二重操作を防げる |
| 3. 結線と振る舞い | 型付き値・フィールド参照、表示へのバインド、Luaの `on_action(ctx, event)`、明示した対象への共有Write | 操作盤のボタンで参照先の箱の色を切り替え、文字表示も連動する |
| 4. 作品として再利用 | 親子関係と別の作品境界、内部参照の付け替え、境界内の一括保存・複製・再配置 | 操作盤と箱を二組複製しても、各ボタンは自分の組の箱だけを操作する |
| 5. 盤面データと反復表示 | サイズ上限のある型付き `GridData` と `GridView`、Luaからの範囲指定更新、フォーカス中のキー入力を段階2のイベントへ変換 | 二人が同じテトリスを操作でき、途中参加・再接続・保存復元でも盤面が一致する |
| 6a. 質感と光 | `Material` の色以外の設定、`Light` | 光るランタンを作れる |
| 6b. 音 | 短い音声アセット、`AudioSource` と再生イベント | 効果音付きスイッチを作れる |
| 6c. 生成形状 | 寸法・分割数・反復数を持つ生成メッシュ | 同期するパラメータで形が変わる造形を作れる |

物体同士の剛体物理、接触イベント、任意アバター装備、汎用粒子、完全なアニメーション編集は、この最初の段階群の後に別計画で扱う。テトリスの完成に必要な部品ではないため、先行条件にしない。

## 段階0で決めるデータの形

`ObjectView` は描画部品のないSlotを表せる。新規作成と複製、保存と同期もこの状態を扱う。`ComponentRegistration` は型ごとにSlot内で固定の `local_id` を持つため、同種のUI要素を複数並べる場合は、それぞれを子Slotに置く。UI要素を一つの大きなJSON配列にまとめない。

パーツの追加・削除は構造コマンドとしてホストが検証する。対象SlotとComponent型、期待revision、初期値を確認し、必要な依存Componentを明示する。削除時はそのComponentを参照するBindingがどうなるかを定義し、孤立参照を黙って別対象へ付け替えない。既存の作業データは保持し、スナップショット形式を変更する場合は再読込を検証してから切り替える。

共有の3D作成パネルは新規の形状、空Slot、WorldText付きSlotを作る。既存SlotのComponentの付け外しとフィールド編集はインスペクタに置く。階層からはWorldText付きの子Slotも作れる。独立したパネル描画・Collider・入力転送を増やさず、[UIの表示先](../guidelines/ui-surfaces.md)と[WorldPanel](../guidelines/world-space-panels.md)の操作規則を使う。

## 操作から表示までの経路

1. Godotはボタンの押下対象と見た目の状態を端末内で扱い、`target`、`action`、`value`、`command_id` を既存の要求Brokerへ渡す。
2. Rustは要求元接続を参加者として照合し、対象Component・イベント型・値域・重複を検証して、ホストのスクリプトまたはSystemへ一度だけ渡す。
3. スクリプトは許可された型付き参照を介して共有Componentの変更を要求する。Rustが競合を確認して確定し、既存の登録表経由で配信・保存する。
4. Godotは確定値からUIと3D表示を再構築する。ボタンのホバーやキーボードフォーカスは各端末のままにする。

`GridData`は200マスを200個のネットワークEntityへ分割せず、上限のあるセル配列として扱う。操作中のピース、スコア、時計は別Componentに置く。更新時に物体全体を再送する現状では、頻繁な盤面更新が配信量へ与える影響を実測し、必要ならフィールド単位の差分を段階5の中で追加する。

作品境界は保存・複製の単位であり、スクリプトの操作権限には使わない。書き込み先は明示された参照・型・値をRustで検証し、共有ワールド内の共同操作を作者や所有者で制限しない。

## 実装と検証の区切り

各段階を独立してレビューできる変更に分ける。共通のコード入口はRustの[`components.rs`](../crates/core/src/components.rs)、[`replication.rs`](../crates/core/src/replication.rs)、構造コマンド、Godotの[`world_panel.gd`](../client-godot/world_panel.gd)、[`world_panels.gd`](../client-godot/world_panels.gd)、作成パネル。新規Componentの追加後は、関連するRustテスト、2クライアント同期、途中参加、保存・復元を確認する。

UIと入力を変更した段階は、実際のレーザー判定からSubViewport、要求Broker、Rustの確定、別クライアントの表示まで `tests/*-integration.mjs --rendered` で確認する。FPSでのマウス捕捉、右クリック保持、Esc、パネル削除、連打、同時操作も含める。段階4では複製した二組の内部参照と、机に置いた作品を再び取り外せることを確認する。段階5では10×20盤面を使い、更新量と描画負荷も測る。
